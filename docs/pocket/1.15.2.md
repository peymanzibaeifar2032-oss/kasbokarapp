### Data and auth boundary
- The backend (PR #13) adds `referralClub` to the full owner export only after `requireAdmin` (same gate as the site's club panel). It runs SELECT-only queries: no `ensureTables`, no `syncReferralRequest`, no outbox marking.
- Exported: member name, phone, code, active/tier, success and total counts, rewards, owner settings, unsent outbox.
- Not exported: referred friends' phones and request ids.
- The app accepts the club only when the export carries a verified owner account. A malformed club is ignored, never partially applied.
- Member codes are only real codes issued by the site. The app never invents a code. With no club loaded it shows "sign in as owner and load from the site (internet required)".
- **Text precedence:** phone edit > site settings > site default.
  - Phone edits: same 4–320 / 4–160 bounds as `saveReferralSettings`, license-gated, stored in localStorage `pocket.referral.v1` and in the JSON backup (`referral`).
  - Saving the site's own text stays an online action in the site panel (link provided). The app does not write site settings.

## «ثبت واریز» per booking (t52u)
- **Site policy (addStudioPayment / tattooBalance):**
  - Integer Toman 1…2,000,000,000; optional note up to 200 characters; no date field.
  - Remaining = max(0, price − paid); settled when paid ≥ price. Overpayment is not rejected, so the app allows it and shows «بیش‌پرداخت».
- **Saving:**
  - Each payment is ONE cash-box income row: `bpay-<uuid>`, `bookingId` = stable local booking id, `bookingServerId` when the booking came from the site.
  - Written by `appendCashEntry` in a single IndexedDB transaction, which also sits behind the license gate.
  - The booking's paid amount = the site export's paid (sum of tattoo_payments) + this phone's rows. The cash box moves exactly once.
- **Double-tap and validation:**
  - One draft id per opened form, plus `getKey` before `add` and a busy state, so a double tap or retry stores nothing extra.
  - Persian, Arabic and Latin digits and separators are accepted. Zero, negative, decimal, NaN and values above 2e9 are rejected.
- **Load from site:**
  - Manual or phone rows are never replaced by the site snapshot (`mergeServerCash` keeps them). Bookings keep `srv-<id>`, so the link survives.
  - The UI says «فقط روی این گوشی ثبت شده و در سایت ثبت نشده است». The site is NOT updated automatically.
  - If the owner also records the same payment on the site, they must delete the phone row in the cash tab. The app does not guess matches.
  - There is no automatic server write. The site's `addStudioPayment` has no idempotency key, so pushing from the phone could double-post.
- **Backup and storage:**
  - JSON backup keeps `bookingId`/`bookingServerId`. Re-importing the same file merges by id, so nothing is counted twice. Old files still import.
  - The cash panel now appends or deletes single rows instead of rewriting the whole box from a possibly stale list.
